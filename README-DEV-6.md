# TileWeaver — довідка для розробки (для себе, Claude)

Це один файл `map-editor.html` (~2280 рядків, HTML+CSS+JS в одному файлі, без збірки).
Живе на GitHub Pages: https://vezunchyk.github.io/TileWeaver (домен tileweaver.online в процесі).
Немає бекенду — все зберігається в `localStorage` браузера користувача.

**Головне правило роботи над цим файлом:** перед будь-якою правкою — `grep -n "^  function \|^  // ----------"`,
щоб знайти точне місце, а не переписувати файл заново. Після правки — завжди:
1. Синтаксична перевірка: `node -e "new Function(fs.readFileSync(...))"` для обох `<script>` блоків.
2. Реальний тест у Playwright (headless Chromium), не "на око". Клікати краще напряму в
   `page.evaluate(() => el.click())`, а не `el.click({force:true})` з Node-сторони Playwright —
   останнє періодично не спрацьовує в цьому середовищі без видимої причини (перевірено на практиці).
3. `wrap.setPointerCapture(...)` обгорнутий в try/catch — не займай, це захист від рідкісного
   зриву всього жесту дотику.

## Модель даних (що зберігається в `project`)

```
project = {
  id, name, gridType: 'iso'|'top'|'side', cellSize,
  tiles: { tileId: {name, img, dataURL} },
  placements: [
    { id, tileId, x, y,           // x,y — ЦІЛІ пікселі, це принципово (див. Історію)
      z,                          // порядок малювання ВСЕРЕДИНІ шару (0-999 умовно, може бути більше)
      layerId,                    // до якого шару належить
      scaleX, scaleY,             // розмір (НЕ примусово підганяється під сітку — жодного авто-стретчу)
      flipX, flipY,               // дзеркала (окремі, незалежні)
      rotation,                   // градуси, 0-360, вільне (не по кроках)
      skewX                       // деформація/перекошування, приблизно -3..3
    }
  ],
  collisions: [ {id, shape:'rect'|'circle', x0,y0,x1,y1} | {id,shape:'circle', x,y,r} ],
  layers: [ {id, name, visible, locked, baseZ} ],  // baseZ — див. "Шари" нижче
  activeLayerId, nextLayerDepth   // лічильник для baseZ нових шарів, ТІЛЬКИ росте
}
```

**Ключове правило**: `z` (об'єкта) і `layerId`/`baseZ` (шару) — це два НЕЗАЛЕЖНІ виміри глибини.
Не зливати їх в одне поле знову (вже була ця помилка й виправлена).

## Як рахується глибина малювання (`comparePlacements`)

```
ефективна_глибина(obj) = getLayer(obj.layerId).baseZ + obj.z
сортування: (ефективна_глибина, потім obj.y як tie-breaker для ізометрії)
```

- `baseZ` шару присвоюється **один раз при створенні** з лічильника `project.nextLayerDepth`,
  який щоразу росте на `LAYER_Z_STEP` (=100, константа на початку скрипта) і ніколи не
  перевикористовується (навіть після видалення шару).
- Крок навмисно з запасом, щоб z окремого об'єкта в жодному разі не перекрив сусідній шар (це
  і була причина бага "трава вище будинків"). Було 1000, зменшено до 100 за проханням
  користувача — якщо колись знадобиться ще менший крок, памʼятай про цей trade-off: "Змінити
  глибину" дозволяє довільне число (аж до ±999999) і теоретично може пробити сусідній шар.
- Кнопки "Підняти"/"Опустити" в шестерні шару — просто `baseZ ± LAYER_Z_STEP`.
- Кнопка "Змінити глибину" — довільне число (+10, -5 і т.д.) до `baseZ`.
- **Об'єднання шарів** (`merge`): бере видимий шар з найбільшим `baseZ` як ціль, для решти —
  `p.z += (їхній_baseZ - baseZ_цілі)`, це ТОЧНО зберігає відносний порядок. НЕ рахувати офсет
  наново від індексу видимих шарів (стара версія, яка й зламала грас/будинки).
- **z нового об'єкта при розміщенні** (`nextZOnLayer(layerId)`): НЕ хардкод `0`. Береться
  максимальний `z` серед усіх плейсментів активного шару, +1. Причина: після `merge()` шар
  може містити плейсменти з дуже різним `z` (мігрували з різних колишніх шарів), і фіксований
  `z:0` для нового обʼєкта міг випадково опинитись у середині цього діапазону — новий обʼєкт
  малювався "під травою". Тепер новий обʼєкт завжди зверху всього, що вже на шарі. Виняток —
  вставка з буфера обміну (paste), там навмисно зберігається `clipboard.z` (відносний z
  скопійованої групи), це інша логіка і її не займати.

## Візуальні "маркери" на виділеному об'єкті

- 4 жовті кутові — зміна розміру (рівномірне, тягнеш за кут, від центру).
- 1 зелений (з'являється тільки в "режимі обертання", після тапу на ↻) — вільне обертання,
  будь-який градус, computed через `atan2` від центру об'єкта.
- 1 рудий (той самий режим) — деформація/нахил (`skewX`), тягнеш вбік.
- В режимі обертання/деформації кутові маркери ховаються, і панель `selPanel` переїжджає
  **під** об'єкт (а не над), бо інакше перекриває зелений маркер зверху.
- Ці маркери НЕ обертаються разом з об'єктом (відома, свідомо прийнята спрощення) — рамка
  виділення й хіт-тест завжди по невернутому (axis-aligned) bbox.

## Автотінь (кнопка 🌑 в панелі виділення)

Бере силует поставленої текстури (canvas `source-in` композиція), сплющує по вертикалі (×0.4),
зафарбовує напівпрозорим темним, ставить як **окремий новий placement**, з нижчим z
(`Math.max(0,p.z-1)`), тим самим шаром, зі зсувом offX=b.w*0.12, offY=b.h*0.32 — **фіксований
відсоток, не пиксель-детекція** (пробував точний пошук нижнього непрозорого пікселя картинки —
користувачу не сподобалось, повернув простий варіант). Одразу виділяється — можна перетягнути,
обернути, деформувати вручну.

## Прив'язка до сітки (snap)

- `Ставити` + прив'язка увімкнена → позиція снепиться, розмір НЕ змінюється (без стретчу).
- `Клон` (лінія/заливка) → завжди снепиться, і теж без примусового стретчу розміру (це було,
  прибрано за проханням користувача — ніякого авто-фіту текстури під клітинку більше немає).
- Для ортогональної сітки (`gridType !== 'iso'`) `cellToWorld`/`worldToCell` рахують ЦЕНТР
  клітинки (не кут!) — була реальна помилка, коли текстура лягала на перетин чотирьох клітинок
  замість центру однієї. Для iso цього бага не було, бо там `isoCell` завжди рахував центр ромба.

## Історія важливих виправлень (щоб не наступати на ті самі граблі)

1. **Шов між тайлами.** Корінь: canvas антиаліасить кожен `drawImage` окремо + дробовий
   devicePixelRatio. Рішення — весь світ малюється в офскрін-буфер 1:1 (без зуму), потім
   ОДНИМ `drawImage` розтягується на екран. Прив'язка буфера — до ФІКСОВАНОЇ цілої world-точки
   (не до дробового pan), інакше при панорамуванні все "смикається" рваними стрибками по
   `zoom`-пікселів (це реально було, виправлено).
2. **Всі координати — цілі пікселі**, завжди (`px()` round), як в Pixel Studio. Перетягування
   рахується від АБСОЛЮТНОЇ точки старту жесту (не інкрементально), щоб не було накопичення
   похибки.
3. **Ізометрична сітка складена не 64×32, а трохи менша (60×30)** — свідоме рішення користувача:
   різниця (по 2px з боків, 1px згори/знизу) — це сама лінія сітки, в яку сусідні тайли трохи
   заходять один на одного, ховаючи будь-який залишковий субпіксельний шов. НЕ "виправляти" це
   назад на чисті 64×32 — вже пробував, стало гірше.
4. **Grid lines для iso** малюються "по пікселях" (Bresenham-подібний алгоритм, ручний
   `fillRect` по клітинках), а не векторним `ctx.stroke()` — бо canvas завжди згладжує похилі
   лінії, і жодного способу це вимкнути через `imageSmoothingEnabled` нема (той прапорець working
   тільки для картинок, не для ліній).
5. **Розмита ручна нарізка спрайта** — прев'ю показується 1:1 (без стиснення), інакше один палець
   на екрані відповідає за кілька реальних пікселів джерела.
6. **Тайл-нарізка (авто/ручна/розумна)** — завжди `imageSmoothingEnabled=false` на всіх тимчасових
   canvas, інакше вирізана текстура виходить розмитою навіть якщо джерело чітке.
7. **`z` і `layerId` шару — незалежні виміри** (детально вище) — не зливати знову.
8. **Гарячі клавіші** — глобальний `keydown` listener (біля paste-логіки, ближче до кінця
   скрипта). Ігнорує подію, якщо фокус в `<input>`/`<textarea>`/contentEditable, інакше Delete
   видаляв би виділений об'єкт замість символу під час перейменування шару чи проєкту.
   - `Delete`/`Backspace` → `deleteSelected()` (для `placement`, `multi`, `collision`)
   - `Ctrl/Cmd+C` → `copySelected()` (аналог кнопок `dup`/`multi-copy`)
   - `Ctrl/Cmd+V` → `doPaste()` (винесено з анонімного `pasteBtn` листенера в іменовану функцію)
   - `Ctrl/Cmd+Z` → `undo()`, `Escape` → зняти виділення
   - Стрілки → `nudgeSelected(dx,dy)`, крок 1 світовий px, `Shift` = крок 10. Тільки для
     `placement`/`multi` — колізії (інша структура даних, rect/circle) поки не рухаються.
9. **Авто-перемикання на `tool='pan'`** після: завершення виділення рамкою (multi-select),
   копіювання (single/multi/Ctrl+C), вставки. Мета — одразу можна тягнути виділене без
   зайвого тапу по кнопці "Перемістити". Якщо додаєш новий спосіб копіювання/виділення —
   постав туди ж `tool='pan'; updateToolButtons();`.
10. **Viewport culling у `render()`** — до сортування й малювання плейсментів тепер спершу
    фільтруємо їх за bbox проти видимої області (`worldX0..worldX0+logicW`,
    `worldY0..worldY0+logicH`, це та сама область, що вже використовувалась для offCanvas).
    До цього `render()` щокадру сортував (`O(n log n)`) і малював (`O(n)`) АБСОЛЮТНО ВСІ
    плейсменти проєкту, навіть ті, що поза екраном — тому великі залиті площі (тисячі тайлів)
    підвішували редактор. Тепер сортується/малюється тільки видима підмножина. Якщо колись
    карти виростуть до десятків тисяч обʼєктів і сам цикл фільтрації (`for` по
    `project.placements`, все ще `O(n)`, просто дешевий bbox-check) стане відчутним —
    наступний крок: просторовий індекс (grid/quadtree) замість лінійного проходу, і те саме
    для `hitTestPlacement`, яка теж лінійно проходить усі плейсменти активного шару.
11. **`scheduleRender()` throttling для pointermove** — усі 11 викликів `render()` всередині
    `wrap.addEventListener('pointermove', ...)` (перетягування, resize/rotate/skew ручок,
    прев'ю заливки, рамка виділення, панорамування, pinch-zoom) замінені на `scheduleRender()`,
    яка через `requestAnimationFrame` схлопує будь-яку кількість викликів за кадр в один
    реальний `render()`. Без цього pointermove міг стріляти частіше за 60 разів/сек (особливо
    з мишею з високим poll rate), і важкі `render()` накопичувались у черзі швидше, ніж
    встигали виконуватись. `render()` напряму (без throttle) лишили для одноразових дій
    (pointerup, кліки, завантаження проєкту) — там затримка в 1 кадр не потрібна.
12. **Дебаунс `saveActiveProject()`** — раніше кожна дрібна дія (кожен розміщений тайл, кожен
    завершений драг) СИНХРОННО серіалізувала ввесь проєкт (`JSON.stringify`), включно з
    base64 `dataURL` усіх тайлів у палітрі, і писала в `localStorage` — це блокує головний
    потік і саме воно найбільше "тупить" після великої заливки, коли `placements` вже
    великий масив. Тепер `saveActiveProject()` лише планує `flushSaveActiveProject()` через
    `setTimeout(400)` і схлопує повторні виклики. **ВАЖЛИВО**: будь-яке місце, де `project`
    підмінюється/перезаписується новими даними (`createProject`, імпорт з файлу, відкриття
    іншого проєкту зі списку) МУСИТЬ спершу викликати `flushSaveActiveProject()` — інакше
    останні 400мс змін попереднього проєкту губляться. Ці виклики вже розставлені в
    `createProject()`, `openProjects()` (перед показом списку) і `loadFileInput` (перед
    імпортом). Якщо додаєш новий спосіб замінити/покинути поточний проєкт — не забудь
    зробити так само. Також є `beforeunload` листенер, що робить `flushSaveActiveProject()`
    при закритті вкладки/сторінки.

## Чому НЕ ділити файл на кілька (`.js`/`.css` окремо)

Питання піднімалось — свідомо не зроблено, і краще не робити без нової явної причини:
розділення файлів на завантаження/парсинг браузером **не впливає** — воно вирішує зовсім іншу
проблему (організація коду, розмір репозиторію), а не швидкість виконання. "Тупить" було
викликано рантайм-логікою (`render()` малював усе, `pointermove` не мав throttle, `save`
блокував потік синхронним `localStorage.setItem` з мегабайтами base64) — усе це однаково
гальмувало б незалежно від того, один файл чи десять. Плюс проєкт свідомо single-file для
простого деплою на GitHub Pages (просто закинути `index.html`, без білд-кроку/бандлера).
Якщо колись файл стане завеликим для комфортної розробки (не для швидкості!) — тоді є сенс
винести в окремі `.js`, але це організаційна, а не перформансна задача.

## Дві тіні замість однієї (`shadow` / `shadowOval`)

Проблема: стара тінь (`act==='shadow'`) бере ПОВНИЙ спрайт обʼєкта, стискає його по висоті
(`flatten=0.4`) і вирізає силует через `source-in`. Для дерев (округла крона) це виглядає
природно — стиснута кругла форма й так читається як тінь. Для прямокутних обʼєктів (будинки,
паркани) стиснута елевація виглядає як "розплавлена" копія самого обʼєкта — реальні тіні так
не падають, і дрібні деталі спрайту (вікна, двері, лінії дощок) лишаються видимими/дірками
всередині форми.

Що зроблено:
1. **`shadow` (🌑, силует)** лишився дефолтним і найкращим для округлих обʼєктів (дерева,
   кущі), але тепер малюється з `octx.filter='blur(2px)'` ПЕРЕД вирізанням альфа-силуету —
   дрібні деталі згладжуються, менше "дірок" у формі. Не чіпає геометрію/офсети, тільки додає
   блюр — безпечна зміна.
2. **`shadowOval` (⬭, новий)** — простий м'який еліпс (radial gradient, без вмісту спрайту
   взагалі), шириною `0.8*bbox.w`, висотою `0.32*bbox.w`. Для будинків/паркану/скринь це
   виглядає природніше, ніж силует-стиск, саме тому що ігнорує форму елевації повністю.
   Обидві кнопки — окремі `act` в тому ж `selPanel` для `type==='placement'`, генерують
   окремий tileId+placement так само як стара `shadow`, тому весь наявний функціонал (можна
   тягнути/масштабувати/видаляти готову тінь) працює однаково для обох.

Якщо і цього не вистачить для якогось конкретного об'єкта — користувач завжди може вручну
підправити готову тінь-плейсмент (перемістити/змасштабувати/дзеркалити), бо це звичайний
plassment як і будь-який інший тайл.

## `normalizeDepths()` — боротьба з "космічними" z/baseZ

Дві причини, чому z/baseZ ставали величезними числами (10000+):
1. `merge()` зсуває `p.z` на різницю `baseZ` шарів, що зливаються — саме собою ОК, зберігає
   порядок, але не зменшує числа.
2. Заливка великої площі (`clone` rect/diamond/line) раніше давала КОЖНОМУ новому тайлу
   `z:nextZOnLayer(...)`, обчислений ВСЕРЕДИНІ циклу — тобто тисяча тайлів заливки з'їдала
   тисячу одиниць z за одну операцію. Виправлено: тепер `nextZOnLayer()` викликається ОДИН
   РАЗ до циклу (`fillZ`/`fillZ2`), і всі тайли однієї заливки отримують ОДНАКОВИЙ z. Це не
   ламає видимий порядок — тайли в одній заливці зазвичай не перекриваються, а Y-координата
   й так є тайбрейком у `comparePlacements`.

Але стара вже збережена карта могла накопичити ці числа ДО фіксу. Тому додано
`normalizeDepths()` (біля `nextZOnLayer`, використовує `LAYER_Z_STEP` з глобальної області):
- Сортує шари за поточним `baseZ` (не за порядком масиву — він міг розʼїхатися після
  ручних "Підняти"/"Опустити"), присвоює нові `baseZ = idx*LAYER_Z_STEP` (0,100,200,...).
- Для кожного шару окремо сортує його плейсменти за старим `z` і присвоює нові `z = 0,1,2,...`
  — маленькі послідовні числа замість "космічних".
- Ефективна глибина (`baseZ+z`) для КОЖНОГО обʼєкта відносно решти зберігається такою ж, як
  була (перевірено тестом — порядок сортування до/після ідентичний), змінюються лише самі
  числа, не порядок.
- Викликається: (1) в `loadProjectData()` одразу після санітизації `layerId` — лікує вже
  зіпсовані старі проєкти автоматично при завантаженні, без окремої кнопки; (2) в кінці
  обробника `merge`; (3) на початку обробника створення нового шару (`addBtn`) — саме це
  прибирає баг "новий шар, а обʼєкти під травою": до фіксу `nextLayerDepth` міг успадкувати
  космічне число від старого злиття, і новий шар опинявся МІЖ старими обʼєктами замість
  строго над ними.

## Панель інструментів обʼєкта (`#selPanel`) тепер переноситься в кілька рядків

Було `white-space:nowrap` — при великій кількості кнопок (mirror/flip/rotate/shadow/
shadowOval/dup/del) рядок вилазив за межі екрана на вузьких дисплеях. Замінено на
`max-width:min(272px, 92vw)` без `nowrap` — кнопки (звичайні inline-елементи з `margin:2px`)
тепер природно переносяться на новий рядок, коли не влазять. Позиціювання панелі (центрування
відносно обʼєкта, затиск у межах екрана) вже враховувало `offsetWidth`/`offsetHeight`, тому
додаткових змін в JS не знадобилось — тільки CSS.

## Відомі свідомі спрощення (не баги, не чіпати без нового прохання)

- Маркери виділення/хіт-тест не обертаються разом з об'єктом.
- Тінь — фіксований відсотковий офсет, не піксель-точна детекція.
- "Розумна нарізка" спрайта: поріг alpha неузгоджений між стартом (>100) і сусідами (>0) —
  теоретично може зліпити два об'єкти з м'якими краями в один. Користувач сказав не займати.
