# TileWeaver — довідка для розробки (для себе, Claude)

Це один файл `map-editor.html` (~2280 рядків, HTML+CSS+JS в одному файлі, без збірки).
Живе на GitHub Pages: https://vezunchyk.github.io/TileWeaver (домен tileweaver.online в процесі).
Немає бекенду — все зберігається в `localStorage` браузера користувача.

**Головне правило роботи над цим файлом:** перед будь-якою правкою — `grep -n "^  function \|^  // ----------"`,
щоб знайти точне місце, а не переписувати файл заново. Після правки — завжди:
1. Синтаксична перевірка: `node -e "new Function(fs.readFileSync(...))"` для обох `<script>` блоків.
2. Реальний тест у Playwright (headless Chromium), не "на око". Клікати краще напряму в
   `page.evaluate(() => el.click())`, а не `el.click({force:true})` з Node-сторони Playwright —
   останнє періодично не спрацьовує в цьому середовищі без видимої причини (перевірено на практиці).
3. `wrap.setPointerCapture(...)` обгорнутий в try/catch — не займай, це захист від рідкісного
   зриву всього жесту дотику.

## Модель даних (що зберігається в `project`)

```
project = {
  id, name, gridType: 'iso'|'top'|'side', cellSize,
  tiles: { tileId: {name, img, dataURL} },
  placements: [
    { id, tileId, x, y,           // x,y — ЦІЛІ пікселі, це принципово (див. Історію)
      z,                          // порядок малювання ВСЕРЕДИНІ шару (0-999 умовно, може бути більше)
      layerId,                    // до якого шару належить
      scaleX, scaleY,             // розмір (НЕ примусово підганяється під сітку — жодного авто-стретчу)
      flipX, flipY,               // дзеркала (окремі, незалежні)
      rotation,                   // градуси, 0-360, вільне (не по кроках)
      skewX                       // деформація/перекошування, приблизно -3..3
    }
  ],
  collisions: [ {id, shape:'rect'|'circle', x0,y0,x1,y1} | {id,shape:'circle', x,y,r} ],
  layers: [ {id, name, visible, locked, baseZ} ],  // baseZ — див. "Шари" нижче
  activeLayerId, nextLayerDepth   // лічильник для baseZ нових шарів, ТІЛЬКИ росте
}
```

**Ключове правило**: `z` (об'єкта) і `layerId`/`baseZ` (шару) — це два НЕЗАЛЕЖНІ виміри глибини.
Не зливати їх в одне поле знову (вже була ця помилка й виправлена).

## Як рахується глибина малювання (`comparePlacements`) — АКТУАЛЬНА МОДЕЛЬ

**УВАГА:** нижче в файлі (розділи "АРХІТЕКТУРНИЙ ФІКС...") лишена історія двох ПОПЕРЕДНІХ
невдалих спроб (адитивна `baseZ+z`, потім лексикографічна `[baseZ, z, y]`) — обидві виявились
не тим, що треба, і замінені. Це — фінальна модель, читай ТІЛЬКИ її для актуальної поведінки:

```
сортування: (obj.z, потім obj.y як tie-breaker для ізометрії)
```

`p.z` — **абсолютне** число. `baseZ` шару в сортуванні НЕ бере участі взагалі.

- `layer.baseZ` — лише підказка, з якого числа почнуться НОВІ обʼєкти на цьому шарі
  (`newPlacementZ(layerId) = getLayer(layerId).baseZ + 1`). Однакове значення для будь-якої
  кількості нових обʼєктів за одну операцію — не зростає з кожним обʼєктом.
- `LAYER_Z_STEP = 10`. Новий шар отримує `baseZ` = `nextLayerBaseZ()` = максимум `baseZ`
  серед ІСНУЮЧИХ ЗАРАЗ шарів `+10`. Рахується щоразу наново від поточного стану, нічого не
  зберігається як лічильник. Видалення шару НЕ чіпає `baseZ` інших шарів.
- "Підняти"/"Опустити" (`±LAYER_Z_STEP` до `baseZ`) впливають ТІЛЬКИ на те, з якого числа
  почнуться майбутні нові обʼєкти на цьому шарі — вже розміщені обʼєкти не перемальовуються
  заднім числом.
- **`merge()` НЕ рахує жодної арифметики над `p.z`** — тільки перепризначає `layerId` на
  цільовий шар (найбільший `baseZ` серед видимих). Оскільки сортування завжди йде за
  абсолютним `p.z`, порядок зберігається сам собою.
- **Жодного автоматичного масового переписування `p.z`/`baseZ` ніде** — ні при завантаженні,
  ні при merge, ні при створенні шару. Якщо користувач вручну поставить конфліктні z на
  різних шарах — це його свідомий вибір, не помилка, яку треба ловити.
- Кнопка "Змінити глибину" — довільне число до `p.z` напряму (не до `baseZ`).
- Вставка з буфера обміну (paste) зберігає `clipboard.z` як є, окрема логіка, не займати.

## Візуальні "маркери" на виділеному об'єкті

- 4 жовті кутові — зміна розміру (рівномірне, тягнеш за кут, від центру).
- 1 зелений (з'являється тільки в "режимі обертання", після тапу на ↻) — вільне обертання,
  будь-який градус, computed через `atan2` від центру об'єкта.
- 1 рудий (той самий режим) — деформація/нахил (`skewX`), тягнеш вбік.
- В режимі обертання/деформації кутові маркери ховаються, і панель `selPanel` переїжджає
  **під** об'єкт (а не над), бо інакше перекриває зелений маркер зверху.
- Ці маркери НЕ обертаються разом з об'єктом (відома, свідомо прийнята спрощення) — рамка
  виділення й хіт-тест завжди по невернутому (axis-aligned) bbox.

## Автотінь (кнопка 🌑 в панелі виділення)

Бере силует поставленої текстури (canvas `source-in` композиція), сплющує по вертикалі (×0.4),
зафарбовує напівпрозорим темним, ставить як **окремий новий placement**, з нижчим z
(`Math.max(0,p.z-1)`), тим самим шаром, зі зсувом offX=b.w*0.12, offY=b.h*0.32 — **фіксований
відсоток, не пиксель-детекція** (пробував точний пошук нижнього непрозорого пікселя картинки —
користувачу не сподобалось, повернув простий варіант). Одразу виділяється — можна перетягнути,
обернути, деформувати вручну.

## Прив'язка до сітки (snap)

- `Ставити` + прив'язка увімкнена → позиція снепиться, розмір НЕ змінюється (без стретчу).
- `Клон` (лінія/заливка) → завжди снепиться, і теж без примусового стретчу розміру (це було,
  прибрано за проханням користувача — ніякого авто-фіту текстури під клітинку більше немає).
- Для ортогональної сітки (`gridType !== 'iso'`) `cellToWorld`/`worldToCell` рахують ЦЕНТР
  клітинки (не кут!) — була реальна помилка, коли текстура лягала на перетин чотирьох клітинок
  замість центру однієї. Для iso цього бага не було, бо там `isoCell` завжди рахував центр ромба.

## Історія важливих виправлень (щоб не наступати на ті самі граблі)

1. **Шов між тайлами.** Корінь: canvas антиаліасить кожен `drawImage` окремо + дробовий
   devicePixelRatio. Рішення — весь світ малюється в офскрін-буфер 1:1 (без зуму), потім
   ОДНИМ `drawImage` розтягується на екран. Прив'язка буфера — до ФІКСОВАНОЇ цілої world-точки
   (не до дробового pan), інакше при панорамуванні все "смикається" рваними стрибками по
   `zoom`-пікселів (це реально було, виправлено).
2. **Всі координати — цілі пікселі**, завжди (`px()` round), як в Pixel Studio. Перетягування
   рахується від АБСОЛЮТНОЇ точки старту жесту (не інкрементально), щоб не було накопичення
   похибки.
3. **Ізометрична сітка складена не 64×32, а трохи менша (60×30)** — свідоме рішення користувача:
   різниця (по 2px з боків, 1px згори/знизу) — це сама лінія сітки, в яку сусідні тайли трохи
   заходять один на одного, ховаючи будь-який залишковий субпіксельний шов. НЕ "виправляти" це
   назад на чисті 64×32 — вже пробував, стало гірше.
4. **Grid lines для iso** малюються "по пікселях" (Bresenham-подібний алгоритм, ручний
   `fillRect` по клітинках), а не векторним `ctx.stroke()` — бо canvas завжди згладжує похилі
   лінії, і жодного способу це вимкнути через `imageSmoothingEnabled` нема (той прапорець working
   тільки для картинок, не для ліній).
5. **Розмита ручна нарізка спрайта** — прев'ю показується 1:1 (без стиснення), інакше один палець
   на екрані відповідає за кілька реальних пікселів джерела.
6. **Тайл-нарізка (авто/ручна/розумна)** — завжди `imageSmoothingEnabled=false` на всіх тимчасових
   canvas, інакше вирізана текстура виходить розмитою навіть якщо джерело чітке.
7. **`z` і `layerId` шару — незалежні виміри** (детально вище) — не зливати знову.
8. **Гарячі клавіші** — глобальний `keydown` listener (біля paste-логіки, ближче до кінця
   скрипта). Ігнорує подію, якщо фокус в `<input>`/`<textarea>`/contentEditable, інакше Delete
   видаляв би виділений об'єкт замість символу під час перейменування шару чи проєкту.
   - `Delete`/`Backspace` → `deleteSelected()` (для `placement`, `multi`, `collision`)
   - `Ctrl/Cmd+C` → `copySelected()` (аналог кнопок `dup`/`multi-copy`)
   - `Ctrl/Cmd+V` → `doPaste()` (винесено з анонімного `pasteBtn` листенера в іменовану функцію)
   - `Ctrl/Cmd+Z` → `undo()`, `Escape` → зняти виділення
   - Стрілки → `nudgeSelected(dx,dy)`, крок 1 світовий px, `Shift` = крок 10. Тільки для
     `placement`/`multi` — колізії (інша структура даних, rect/circle) поки не рухаються.
9. **Авто-перемикання на `tool='pan'`** після: завершення виділення рамкою (multi-select),
   копіювання (single/multi/Ctrl+C), вставки. Мета — одразу можна тягнути виділене без
   зайвого тапу по кнопці "Перемістити". Якщо додаєш новий спосіб копіювання/виділення —
   постав туди ж `tool='pan'; updateToolButtons();`.
10. **Viewport culling у `render()`** — до сортування й малювання плейсментів тепер спершу
    фільтруємо їх за bbox проти видимої області (`worldX0..worldX0+logicW`,
    `worldY0..worldY0+logicH`, це та сама область, що вже використовувалась для offCanvas).
    До цього `render()` щокадру сортував (`O(n log n)`) і малював (`O(n)`) АБСОЛЮТНО ВСІ
    плейсменти проєкту, навіть ті, що поза екраном — тому великі залиті площі (тисячі тайлів)
    підвішували редактор. Тепер сортується/малюється тільки видима підмножина. Якщо колись
    карти виростуть до десятків тисяч обʼєктів і сам цикл фільтрації (`for` по
    `project.placements`, все ще `O(n)`, просто дешевий bbox-check) стане відчутним —
    наступний крок: просторовий індекс (grid/quadtree) замість лінійного проходу, і те саме
    для `hitTestPlacement`, яка теж лінійно проходить усі плейсменти активного шару.
11. **`scheduleRender()` throttling для pointermove** — усі 11 викликів `render()` всередині
    `wrap.addEventListener('pointermove', ...)` (перетягування, resize/rotate/skew ручок,
    прев'ю заливки, рамка виділення, панорамування, pinch-zoom) замінені на `scheduleRender()`,
    яка через `requestAnimationFrame` схлопує будь-яку кількість викликів за кадр в один
    реальний `render()`. Без цього pointermove міг стріляти частіше за 60 разів/сек (особливо
    з мишею з високим poll rate), і важкі `render()` накопичувались у черзі швидше, ніж
    встигали виконуватись. `render()` напряму (без throttle) лишили для одноразових дій
    (pointerup, кліки, завантаження проєкту) — там затримка в 1 кадр не потрібна.
12. **Дебаунс `saveActiveProject()`** — раніше кожна дрібна дія (кожен розміщений тайл, кожен
    завершений драг) СИНХРОННО серіалізувала ввесь проєкт (`JSON.stringify`), включно з
    base64 `dataURL` усіх тайлів у палітрі, і писала в `localStorage` — це блокує головний
    потік і саме воно найбільше "тупить" після великої заливки, коли `placements` вже
    великий масив. Тепер `saveActiveProject()` лише планує `flushSaveActiveProject()` через
    `setTimeout(400)` і схлопує повторні виклики. **ВАЖЛИВО**: будь-яке місце, де `project`
    підмінюється/перезаписується новими даними (`createProject`, імпорт з файлу, відкриття
    іншого проєкту зі списку) МУСИТЬ спершу викликати `flushSaveActiveProject()` — інакше
    останні 400мс змін попереднього проєкту губляться. Ці виклики вже розставлені в
    `createProject()`, `openProjects()` (перед показом списку) і `loadFileInput` (перед
    імпортом). Якщо додаєш новий спосіб замінити/покинути поточний проєкт — не забудь
    зробити так само. Також є `beforeunload` листенер, що робить `flushSaveActiveProject()`
    при закритті вкладки/сторінки.

## Чому НЕ ділити файл на кілька (`.js`/`.css` окремо)

Питання піднімалось — свідомо не зроблено, і краще не робити без нової явної причини:
розділення файлів на завантаження/парсинг браузером **не впливає** — воно вирішує зовсім іншу
проблему (організація коду, розмір репозиторію), а не швидкість виконання. "Тупить" було
викликано рантайм-логікою (`render()` малював усе, `pointermove` не мав throttle, `save`
блокував потік синхронним `localStorage.setItem` з мегабайтами base64) — усе це однаково
гальмувало б незалежно від того, один файл чи десять. Плюс проєкт свідомо single-file для
простого деплою на GitHub Pages (просто закинути `index.html`, без білд-кроку/бандлера).
Якщо колись файл стане завеликим для комфортної розробки (не для швидкості!) — тоді є сенс
винести в окремі `.js`, але це організаційна, а не перформансна задача.

## Дві тіні замість однієї (`shadow` / `shadowOval`)

Проблема: стара тінь (`act==='shadow'`) бере ПОВНИЙ спрайт обʼєкта, стискає його по висоті
(`flatten=0.4`) і вирізає силует через `source-in`. Для дерев (округла крона) це виглядає
природно — стиснута кругла форма й так читається як тінь. Для прямокутних обʼєктів (будинки,
паркани) стиснута елевація виглядає як "розплавлена" копія самого обʼєкта — реальні тіні так
не падають, і дрібні деталі спрайту (вікна, двері, лінії дощок) лишаються видимими/дірками
всередині форми.

Що зроблено:
1. **`shadow` (🌑, силует)** лишився дефолтним і найкращим для округлих обʼєктів (дерева,
   кущі), але тепер малюється з `octx.filter='blur(2px)'` ПЕРЕД вирізанням альфа-силуету —
   дрібні деталі згладжуються, менше "дірок" у формі. Не чіпає геометрію/офсети, тільки додає
   блюр — безпечна зміна.
2. **`shadowOval` (⬭, новий)** — простий м'який еліпс (radial gradient, без вмісту спрайту
   взагалі), шириною `0.8*bbox.w`, висотою `0.32*bbox.w`. Для будинків/паркану/скринь це
   виглядає природніше, ніж силует-стиск, саме тому що ігнорує форму елевації повністю.
   Обидві кнопки — окремі `act` в тому ж `selPanel` для `type==='placement'`, генерують
   окремий tileId+placement так само як стара `shadow`, тому весь наявний функціонал (можна
   тягнути/масштабувати/видаляти готову тінь) працює однаково для обох.

Якщо і цього не вистачить для якогось конкретного об'єкта — користувач завжди може вручну
підправити готову тінь-плейсмент (перемістити/змасштабувати/дзеркалити), бо це звичайний
plassment як і будь-який інший тайл.

## [ЗАСТАРІЛО, ВИДАЛЕНО] `normalizeDepths()` — боротьба з "космічними" z/baseZ

**Ця функція та все нижче в цьому розділі повністю ВИДАЛЕНІ з коду.** Залишено як історія
чому саме такий підхід не спрацював — щоб не винаходити його знову. Дивись розділ
"Як рахується глибина малювання — АКТУАЛЬНА МОДЕЛЬ" на початку файлу для чинної поведінки.

Дві причини, чому z/baseZ ставали величезними числами (10000+):
1. `merge()` зсуває `p.z` на різницю `baseZ` шарів, що зливаються — саме собою ОК, зберігає
   порядок, але не зменшує числа.
2. Заливка великої площі (`clone` rect/diamond/line) раніше давала КОЖНОМУ новому тайлу
   `z:nextZOnLayer(...)`, обчислений ВСЕРЕДИНІ циклу — тобто тисяча тайлів заливки з'їдала
   тисячу одиниць z за одну операцію. Виправлено: тепер `nextZOnLayer()` викликається ОДИН
   РАЗ до циклу (`fillZ`/`fillZ2`), і всі тайли однієї заливки отримують ОДНАКОВИЙ z. Це не
   ламає видимий порядок — тайли в одній заливці зазвичай не перекриваються, а Y-координата
   й так є тайбрейком у `comparePlacements`.

Але стара вже збережена карта могла накопичити ці числа ДО фіксу. Тому додано
`normalizeDepths()` (біля `nextZOnLayer`, використовує `LAYER_Z_STEP` з глобальної області):
- Сортує шари за поточним `baseZ` (не за порядком масиву — він міг розʼїхатися після
  ручних "Підняти"/"Опустити"), присвоює нові `baseZ = idx*LAYER_Z_STEP` (0,100,200,...).
- Для кожного шару окремо сортує його плейсменти за старим `z` і присвоює нові `z = 0,1,2,...`
  — маленькі послідовні числа замість "космічних".
- Ефективна глибина (`baseZ+z`) для КОЖНОГО обʼєкта відносно решти зберігається такою ж, як
  була (перевірено тестом — порядок сортування до/після ідентичний), змінюються лише самі
  числа, не порядок.
- Викликається: (1) в `loadProjectData()` одразу після санітизації `layerId` — лікує вже
  зіпсовані старі проєкти автоматично при завантаженні, без окремої кнопки; (2) в кінці
  обробника `merge`; (3) на початку обробника створення нового шару (`addBtn`) — саме це
  прибирає баг "новий шар, а обʼєкти під травою": до фіксу `nextLayerDepth` міг успадкувати
  космічне число від старого злиття, і новий шар опинявся МІЖ старими обʼєктами замість
  строго над ними.

## Панель інструментів обʼєкта (`#selPanel`) тепер переноситься в кілька рядків

Було `white-space:nowrap` — при великій кількості кнопок (mirror/flip/rotate/shadow/
shadowOval/dup/del) рядок вилазив за межі екрана на вузьких дисплеях. Замінено на
`max-width:min(272px, 92vw)` без `nowrap` — кнопки (звичайні inline-елементи з `margin:2px`)
тепер природно переносяться на новий рядок, коли не влазять. Позиціювання панелі (центрування
відносно обʼєкта, затиск у межах екрана) вже враховувало `offsetWidth`/`offsetHeight`, тому
додаткових змін в JS не знадобилось — тільки CSS.

## Обрізка прозорих полів перед силует-тінню (продовження "Дві тіні")

Проблема з "ромбовим"/"перетікає в траву" виглядом тіні на будинках: старий код брав ВВЕСЬ
canvas спрайту (`iw x ih`) для силуету, включно з будь-яким прозорим запасом навколо
намальованого обʼєкта (типово для ізометричних тайлів — щоб влізти в однаковий розмір
клітинки). При стисканні по висоті цей запас стискається РАЗОМ з малюнком, тож форма виходить
ширшою й іншою, ніж сам обʼєкт — саме це, найімовірніше, і давало той "ромб, що обтікає траву".

Фікс: перед стисканням скануємо альфа-канал спрайту (`getImageData`), знаходимо тісний
bounding box непрозорих пікселів (`minCX/minCY/maxCX/maxCY`, поріг альфи >10), і стискаємо
ТІЛЬКИ цю обрізану область, а не весь канвас. `scale = b.w/iw` перераховує обрізану ширину/
висоту в ті самі світові одиниці, що й раніше. Обгорнуто в `try/catch` — якщо з якоїсь причини
`getImageData` недоступний (напр. tainted canvas), тихо відкатується на повний кадр без обрізки
(стара поведінка), нічого не ламається.

**Якщо і після цього діамантовий артефакт лишається** — ймовірно, справа не в прозорих полях,
а в тому, що сам PNG будинку містить намальовану непрозору діамантову підложку/траву під
стінами (частий прийом в ізо-тайлсетах для безшовного суміщення з сіткою) — тоді alpha-бокс
включатиме її, бо вона фактично непрозора. У такому разі це вже не піддається автоматичному
виправленню без аналізу вмісту зображення — треба або підрізати сам сирцевий PNG (прибрати
підложку з файлу), або просто використовувати **⬭ (тінь-еліпс)** для таких обʼєктів — вона
взагалі ігнорує вміст спрайту і тому не може успадкувати цей артефакт.

## Дрібні UX-фікси (перетягування ховає панель, тінь одразу під рукою, дедуп undo)

- **"Оранжева цятка", що не зникала**: `hideHandles()` приховувала `hTL/hTR/hBL/hBR` і
  `hRot`, але ЗАБУВАЛА приховати `hSkew` (ручка перекосу, той самий помаранчевий
  `.resize-handle` гурток). Якщо ручка перекосу колись показувалась і потім виділення
  знімалось через будь-який з шляхів `hideHandles()` (а не через повний `updateHandles()`,
  де обидва явно ховались на старті) — вона лишалась висіти на екрані назавжди, аж доки
  щось інше (типу створення нового проєкту) не перемальовувало DOM. Виправлено: `hideHandles()`
  тепер явно ховає і `hSkew` теж.

- **`updateSelPanel()` ховає саму панель кнопок (не хендли)**, поки триває активний драг:
  `mode` дорівнює `dragMove`/`multiDragMove`/`resizeHandle`/`rotateHandle`/`skewHandle`/
  `dragMoveRect`/`resizeCollisionRect`. Раніше панель кнопок (mirror/rotate/shadow/...)
  перемальовувалась і слідувала за обʼєктом щокадру навіть під час перетягування — затуляла
  саме те місце, куди тягнеш. Хендли (кутові точки) лишили видимими — це самі ручки драгу, не
  заважають. Реалізовано через `dragging ? 'none' : 'block'` замість завжди `'block'`.
- **Тінь одразу готова для переміщення**: обидва обробники (`shadow`, `shadowOval`) вже
  виставляли `selected = {type:'placement', id:np.id}` на новостворену тінь — додано ще
  `tool='pan'; updateToolButtons();` одразу після, щоб не треба було вручну перемикати
  інструмент перед тим як тягнути тінь на місце (як і в інших місцях — copy/paste/marquee).
- **Дедуплікація `pushUndo()`**: скарга "Скасувати не працює після видалення шару" — причина
  в тому, що кілька дій поспіль (зокрема старт будь-якого драгу викликає `pushUndo()` одразу
  на pointerdown, ще ДО зміни) можуть штовхнути в стек кілька ІДЕНТИЧНИХ знімків стану, якщо
  між ними нічого реально не змінилось (тап-вибір без руху тощо). Тоді один клік "Скасувати"
  просто відкочує до стану, який виглядає так само як поточний — візуально "нічого не сталось",
  і доводиться тиснути кілька разів. Виправлено: `pushUndo()` тепер порівнює новий знімок з
  верхівкою стеку і не дублює, якщо вони однакові.

## [ЗАСТАРІЛО, ЗАМІНЕНО] АРХІТЕКТУРНИЙ ФІКС: `comparePlacements` тепер лексикографічний, не адитивний

**Це теж замінено — лексикографічне порівняння `[baseZ, z, y]` описане нижче більше НЕ
використовується.** Причина: воно все ще прив'язувало сортування до `baseZ` шару, а
користувач прямо попросив, щоб `merge()` не чіпав `p.z` ВЗАГАЛІ і щоб z був простим
абсолютним числом без жодних формул. Дивись фінальний розділ
"АРХІТЕКТУРНИЙ ФІКС #2 (ФІНАЛЬНИЙ)" нижче та розділ на початку файлу для чинної моделі.
Залишено як історія, щоб не повторити той самий хід думки.

Це найважливіша зміна в файлі щодо z-глибини — читай перед тим, як чіпати щось повʼязане з
`z`/`baseZ`/шарами.

**Стара, ПОМИЛКОВА модель:** `effectiveDepth = baseZ + z`, одне число. Проблема: якщо `z`
на якомусь шарі виростав більшим за `LAYER_Z_STEP` (заливка великої площі, merge, купа
окремих тапів по одному — кожен зі своїм z), він **арифметично протікав** у діапазон
СУСІДНЬОГО шару. Приклад: шар A має `baseZ=0` і містить обʼєкт з `z=500` (бо туди натикали
500 окремих тайлів і кожен колись отримав свій +1); новий шар B створюється з `baseZ=100`
(на `LAYER_Z_STEP` вище) — але `effectiveDepth` того обʼєкта з шару A (`0+500=500`) БІЛЬШИЙ
за `effectiveDepth` щойно розміщеного обʼєкта на шарі B (`100+0=100`) — тобто шар A
"з'їдає" шар B, хоч він і створений пізніше з більшим `baseZ`. Це і була причина стійкого
багу "новий шар — обʼєкти під старим шаром", який не лікувався жодним підбором
`LAYER_Z_STEP` чи `normalizeDepths()`, бо сама формула порівняння була хибною по суті —
будь-яке досить велике `z` МОЖЕ пробити будь-який скінченний крок між шарами.

**Нова, ПРАВИЛЬНА модель:** `comparePlacements(a,b)` порівнює `baseZ` шарів
БЕЗПОСЕРЕДНЬО (`za !== zb ? za-zb : ...`) — це ПЕРШИЙ і вирішальний критерій. Тільки якщо
обʼєкти на ОДНОМУ Й ТОМУ Ж шарі, тоді порівнюється `z` (і далі `y` як тайбрейк). Це
лексикографічне порівняння `[layerBaseZ, z, y]`, а не сума. Наслідок: **шар як межа
порядку малювання тепер абсолютний і непробивний** — жодне число `z`, хоч би яким великим
воно було, не може змусити обʼєкт з нижчого шару намалюватись НАД обʼєктом з вищого шару.
`LAYER_Z_STEP` (100) тепер має значення лише щоб `baseZ` різних шарів були РІЗНИМИ числами
— конкретна величина кроку більше не впливає на коректність.

**Наслідок для генерації нових обʼєктів:** оскільки міжшарова безпека більше не залежить від
величини `z`, забрали `nextZOnLayer()` (яка й давала кожному новому обʼєкту `max+1`,
джерело "космічних" чисел і того, що "у кожної травинки інший z"). Тепер константа
`NEW_PLACEMENT_Z = 0` — усі новостворені обʼєкти (одиночний тап, заливка лінією/
прямокутником/ромбом) отримують ОДНАКОВИЙ `z=0`. Порядок серед однакових-`z` обʼєктів на
одному шарі визначає `y`-координата — це й так природний тайбрейк для ізометрії, додаткове
числo не потрібне. `normalizeDepths()` лишили для чищення СТАРИХ вже збережених даних із
завеликими числами (косметика/читабельність панелі "Порядок NN"), але коректність
розшарування від неї більше не залежить.

**Якщо колись знову зʼявиться спокуса повернути "завжди зверху" логіку (`max+1`) —
не робити через додавання до baseZ.** Якщо знадобиться гарантія "новий обʼєкт малюється над
усім старим НА ТОМУ Ж ШАРІ" — рахувати `max(z)+1` виключно як внутрішньошаровий тайбрейк
(він і так ізольований від інших шарів завдяки лексикографічному порівнянню), і тоді
зростання числа не є проблемою для міжшарового порядку — хіба що знову стане "некрасивим"
косметично, тому варто періодично прогонити через `normalizeDepths()`.

## АРХІТЕКТУРНИЙ ФІКС #2 (ФІНАЛЬНИЙ, ЧИННИЙ) — z абсолютний, нуль автоматики

Обидва попередні підходи вище (адитивний `baseZ+z`, потім лексикографічний `[baseZ,z,y]`)
замінені за прямою вимогою користувача. Повна специфікація — на початку файлу в розділі
"Як рахується глибина малювання — АКТУАЛЬНА МОДЕЛЬ". Коротко, що змінилось порівняно з
лексикографічною версією:

1. `comparePlacements` = `((a.z||0)-(b.z||0)) || (a.y-b.y)` — жодного `getLayer()`, жодного
   `baseZ` в сортуванні взагалі. `p.z` — самодостатнє абсолютне число.
2. `LAYER_Z_STEP` зменшено до **10** (було 100).
3. `project.nextLayerDepth` (персистентний лічильник) ВИДАЛЕНО. Замість нього —
   `nextLayerBaseZ()`: рахує `max(існуючі baseZ)+LAYER_Z_STEP` щоразу наново, не зберігає
   стан. Це означає: видалив шар — лічильник "забув" про нього, як і хотів користувач.
4. `normalizeDepths()` ВИДАЛЕНО ПОВНІСТЮ (усі виклики теж) — жодного автоматичного масового
   переписування `z`/`baseZ` більше немає ніде: ні при завантаженні, ні при merge, ні при
   створенні шару. Явна вимога користувача: "не потрібно робити хуй зна які формули які все
   ламають".
5. `nextZOnLayer()`/`NEW_PLACEMENT_Z` замінені на `newPlacementZ(layerId)` =
   `getLayer(layerId).baseZ + 1` — однакове число для БУДЬ-ЯКОЇ кількості нових обʼєктів за
   раз, не лічильник, що росте.
6. `merge()` більше не робить `p.z += (...)` — тільки `p.layerId = targetLayer.id`. Нуль
   арифметики над z. "Я обʼєдную шари — всі залишаються при своїх z" (пряма вимога).
7. "Підняти"/"Опустити" шар — тепер стосуються ТІЛЬКИ майбутніх нових обʼєктів
   (`newPlacementZ` читає актуальний `baseZ`), не чіпають вже розміщені.

**Якщо користувач поскаржиться на "залишки космічних z" зі старих даних** — це очікувано і
свідомо (п.4): ніхто нічого не переписує заднім числом. Пропонувати ручне виправлення через
"Змінити глибину" для конкретних проблемних обʼєктів, а не новий авто-фікс.

## Відомі свідомі спрощення (не баги, не чіпати без нового прохання)

- Маркери виділення/хіт-тест не обертаються разом з об'єктом.
- Тінь — фіксований відсотковий офсет, не піксель-точна детекція.
- "Розумна нарізка" спрайта: поріг alpha неузгоджений між стартом (>100) і сусідами (>0) —
  теоретично може зліпити два об'єкти з м'якими краями в один. Користувач сказав не займати.

## Технічний борг / дрібниці, які можна колись прибрати

- `getLayerOrder()` — функція-сирота, більше ніде не використовується після переходу на `baseZ`.
- `findGroundContactFraction()` — написана для точної тіні, зараз НЕ використовується (тінь
  повернули на простий відсоток), лишилась в коді про запас, якщо колись повернемось до ідеї.

## Тінь: `z` = такий самий, як в обʼєкта (не `p.z-1`)

За прямим проханням користувача обидва генератори тіні (`shadow`, `shadowOval`) тепер
ставлять тіні `z: p.z` замість `z: Math.max(0, p.z-1)`. **Важливий нюанс, який варто
памʼятати:** оскільки `comparePlacements` тайбрейкає рівні `z` за `y`, а тінь навмисно
зміщена ВНИЗ відносно обʼєкта (`offY`/`offY2` — додатні, "тінь падає вниз-праворуч"), при
однаковому `z` тінь матиме БІЛЬШИЙ `y` і теоретично сортуватиметься ПІСЛЯ обʼєкта (тобто
малюватиметься зверху, а не знизу). На практиці це не мало б сильно впадати в очі — тінь
напівпрозора (`rgba(10,10,10,0.45)`) і перекриває хіба що нижню частину/основу самого
спрайту, що часто виглядає нормально (обʼєкт "стоїть у власній тіні"). Якщо після
тестування користувач скаже, що тінь тепер видима "поверх" обʼєкта і це виглядає погано —
варіанти для наступного разу: (а) трохи зменшити `offY`/`offY2`, щоб тінь не заходила так
далеко за центр обʼєкта; (б) додати окреме поле сортування, що не завʼязане на `y` (складніше,
поки не чіпати без потреби).

## Кнопка видалення обʼєкта: іконка + підтвердження

Причина: у режимі "рука" при активному перетягуванні великих текстових кнопок "Видалити"
(на весь ряд) було легко випадково зачепити й видалити обʼєкт. Зроблено:
- Текст кнопки замінено на іконку 🗑 (три місця: одиночний `placement`, `collision`,
  `multi-del`), з `title="Видалити"` для підказки на десктопі.
- CSS `.del` звужено (`padding:6px 10px; min-width:0`) — менша площа випадкового тапу.
- Перед фактичним видаленням тепер `confirm()` — нативний діалог браузера/системи. Один
  випадковий тап більше не видаляє обʼєкт одразу, потрібне явне підтвердження другим тапом
  у діалозі. Реалізовано у всіх трьох місцях (`del` для placement, `del` для collision,
  `multi-del`), з `pushUndo()` та фактичним видаленням ТІЛЬКИ після підтвердження (`return`
  одразу, якщо `confirm()` повернув `false`).

## Довге натискання в палітрі тайлів більше не спрацьовує від скролу

Було: `touchstart` на кнопці тайла запускав `setTimeout(...,500)` для відкриття
редагування/видалення тайла, а скасовувався лише на `touchend`. Якщо користувач просто
гортав палітру (горизонтальний скрол, `#palette{overflow-x:auto}`) і тримав палець на екрані
довше 500мс (звичайна річ для повільного/плавного свайпу) — таймер спрацьовував і відкривав
вікно редагування ПІД ЧАС скролу, хоча користувач нічого довго не тримав на місці.

Фікс: додано відстеження позиції старту дотику (`tsX`/`tsY`) і `touchmove` слухач — якщо
палець зрушився більше ніж на 8px в будь-якому напрямку, таймер скасовується
(`tsCancelled=true; clearTimeout(timer)`) і вікно вже НЕ відкриється, навіть якщо початковий
таймаут ще не вийшов. Також додано `touchcancel` для повноти (на випадок переривання жесту
системою). Поріг 550мс (було 500) — незначне збільшення про запас, основний фікс саме в
скасуванні при русі, а не в тривалості.

## Блокування окремого обʼєкта (`p.locked`)

Нове поле `locked` (boolean) на плейсменті (не на колізії — користувач просив саме про
обʼєкти/тайли, колізії не чіпав). Поведінка:

- **Кнопка 🔓 "Заблокувати"** в панелі виділення — блокує БЕЗ підтвердження (блокувати
  можна вільно, шкоди немає). Одразу знімає виділення (`selected=null`) — щоб панель
  заблокованого обʼєкта відкрилась заново при наступному тапі, а не показувала стару
  розблоковану панель поверх щойно заблокованого стану.
- Коли `p.locked===true`, `updateSelPanel()` показує ТІЛЬКИ кнопку
  `<button data-act="unlock">🔒 Розблокувати</button>` — жодних mirror/rotate/shadow/dup/del.
  Хендли (кутові точки) теж ховаються (`hideHandles()`).
- **Розблокування вимагає `confirm()`** — пряма вимога користувача.
- **`pointerdown` для інструмента "рука"**: на самому вході в гілку
  `tool==='pan' && selected && selected.type==='placement'` — якщо `p.locked`, одразу
  `return` (жодного `resizeHandle`/`rotateHandle`/`skewHandle`/`dragMove`). Заблокований
  обʼєкт можна ВИБРАТИ тапом (щоб дістатись кнопки розблокування — `hitTestPlacement` не
  фільтрує по `p.locked`), але не можна тягнути/масштабувати/обертати.
- **Marquee (виділення рамкою)**: заблоковані обʼєкти виключаються зі списку `selIds` — не
  потрапляють у групове виділення, тому не можуть бути випадково зачеплені груповим драгом.

**Якщо колись знадобиться блокування для колізій теж** — той самий патерн (`s.locked`),
просто перенести аналогічні перевірки в гілку `tool==='pan' && selected.type==='collision'`.

## Порядок шарів у смузі (`renderLayersStrip`): новий шар — праворуч, не ліворуч

Був баг: `displayLayers = project.layers.slice().sort(function(a,b){ return (b.baseZ||0)-(a.baseZ||0); })`
— сортування ЗА СПАДАННЯМ `baseZ`. Оскільки новостворений шар завжди має НАЙБІЛЬШИЙ `baseZ`
(див. `nextLayerBaseZ()`), він опинявся ПЕРШИМ в масиві — а `forEach`+`appendChild` в
`display:flex` рядок ставить елементи зліва направо в порядку ітерації — тобто новий шар
малювався найлівішим. Як у більшості редакторів (і як очікував користувач) має бути навпаки:
перший створений шар — зліва, кожен новий — правіше. Виправлено на сортування ЗА
ЗРОСТАННЯМ (`(a.baseZ||0)-(b.baseZ||0)`). Також додано `layersStrip.scrollLeft =
layersStrip.scrollWidth;` одразу після створення нового шару — якщо смуга не влазить на
екран, вона одразу прокручується так, щоб новий (найправіший) шар було видно без ручного
скролу.

**Важливо:** це суто ВІЗУАЛЬНЕ сортування для відображення (`displayLayers` — локальна
копія, `.slice()`). Реальний масив `project.layers` (порядок збереження, `activeLayerId`,
всі інші посилання по `id`) не чіпається і не пересортовується.

## Кнопка ока на панелі виділення (сховати / перетягнути й запамʼятати позицію)

Нова кнопка 👁 (`data-act="panelEye"`) — перша в `innerHTML` панелі виділення, додана в УСІХ
чотирьох варіантах панелі (multi, placement звичайний, placement заблокований, collision) через
спільну константу `EYE_BTN_HTML`.

- **Короткий тап** → `selPanelHidden = !selPanelHidden`. Коли `true`, `updateSelPanel()`
  ПОВНІСТЮ перезаписує `innerHTML` на саме око (`if(selPanelHidden){ selPanel.innerHTML =
  EYE_BTN_HTML; hideHandles(); }` — в самому кінці функції, після всієї branch-логіки,
  щоб перекрити що завгодно, що було побудовано вище). Око лишається тапабельним, щоб
  повернути повну панель.
- **Утримання (400мс) без руху** → активує drag-режим панелі: `pointerdown` на кнопці ока
  запускає таймер; якщо палець руху більше ніж на 8px ДО спрацювання таймера — це просто
  скрол/випадковий рух, `clearTimeout`, drag не активується. Якщо таймер спрацював — кожен
  наступний `pointermove` (на `document`, не на кнопці — щоб палець міг вийти за межі самої
  кнопки під час перетягування) оновлює `selPanel.style.left/top` напряму.
- **Відпускання після drag** → фінальна позиція зберігається в `selPanelCustomPos = {left,
  top}` (модульна змінна, НЕ привʼязана до конкретного обʼєкта). Також ставиться
  `selPanelJustDragged = true`, щоб `click`, який неминуче настане одразу після `pointerup`,
  не був помилково розцінений як "тап по оку" і не перемкнув `selPanelHidden` одразу після
  щойно завершеного перетягування.
- **`selPanelCustomPos` персистентний між виділеннями**: в кінці `updateSelPanel()`, якщо
  `selPanelCustomPos` заданий — використовується ВІН замість обчисленого `screenPt`
  (позиції під обʼєктом). Тобто після одного перетягування панель буде з'являтися в ТОМУ Ж
  місці екрана для будь-якого наступного виділеного обʼєкта, аж доки користувач не перетягне
  її знову. `selPanelHidden` так само не скидається при зміні виділення — обидва стани
  ("де" і "показана чи ні") трактуються як налаштування самої панелі, а не конкретного
  обʼєкта.
- Обидва стани (`selPanelHidden`, `selPanelCustomPos`) НЕ зберігаються в localStorage/
  проєкті — це суто сесійний UI-стан, скидається при перезавантаженні сторінки. Якщо
  колись попросять зробити персистентним між сесіями — просто дописати в
  `serializeProject()`/`loadProjectData()`.

**Баг "панель тікає назад під час перетягування" і фікс:** `document.addEventListener` для
`pointermove`/`pointerup` не зупиняв дальше поширення події — вона все одно доходила (через
бабблінг вгору) до власного `pointermove`-обробника `wrap` (canvas), який викликав
`scheduleRender()` → `render()` → `updateSelPanel()`, а та (поки `selPanelCustomPos` ще не
встановлений — драг не завершився) перераховувала `left`/`top` під обʼєктом і перебивала
щойно виставлену рукою позицію. Візуально — панель "стрибала" назад щокадру під час тягання.

Фікс — подвійний захист:
1. `e2.stopPropagation()` додано і в `onMove`, і в `onUp` (раніше стояв лише в `onMove`... ні,
   раніше не стояв узагалі ні в `onMove`, ні в `onUp` — лише в початковому `pointerdown`,
   якого досить для блокування ТІЛЬКИ першої події, але не наступних `pointermove`).
2. Прапорець `draggingPanelPos` (`true` між `holdTimer` і `onUp`) — `updateSelPanel()` тепер
   перевіряє його ПЕРЕД тим, як чіпати `left`/`top`, і виходить одразу (`return`), якщо
   перетягування триває. Це запасний захист на випадок, якщо `render()` все ж викликається
   з якогось іншого джерела (не з `wrap`'s pointermove) під час драгу.

## Колізії: перемістити/видалити/копіювати/заблокувати — тепер повноцінно

Раніше панель колізії мала ЛИШЕ кнопку видалення. Переміщення й ресайз технічно ВЖЕ
працювали, але тільки в інструменті "Рука" — а поки активний інструмент "Колізії", тап на
вже існуючу колізію завжди малював НОВУ поверх, без жодного способу вибрати стару. Це і
виглядало як "не можна перемістити".

Що зроблено:
- **`tool==='collision'` тепер спершу перевіряє `hitTestCollision()`** на місці тапу. Якщо
  влучили в ІСНУЮЧУ колізію — вибираємо її, перемикаємо `tool='pan'`, і одразу входимо в
  `dragMove`/`dragMoveRect` (якщо не заблокована) — можна тягнути з того самого жесту, без
  окремого тапу для вибору. Якщо не влучили — як і раніше, малюємо нову форму.
  Режим `collisionMode==='texture'` (авто-колізія по тайлу, окрема гілка в `tapPending`) не
  зачеплено.
- **`s.locked`** (за тим самим патерном, що й `p.locked` для плейсментів): заблокована
  колізія не тягнеться і не ресайзиться (перевірка на вході в `tool==='pan' &&
  selected.type==='collision'` гілку, і в прямому виборі через `hitAnyC.locked`). Панель
  показує тільки `🔒 Розблокувати` (з `confirm()`), інакше — `🔓 Заблокувати` (без
  підтвердження) серед інших кнопок.
- **`cdup`** — копіювання колізії: створює нову з тим самим розміром, зсунуту на +16/+16
  світових одиниць, одразу вибирає її і перемикає на "руку" (як і інші місця з копіюванням
  в проєкті). НЕ використовує систему `clipboard`/paste (та заточена під плейсменти з
  tileId/z/scale) — для простих форм-колізій пряме клонування простіше й достатнє.
- **"Перевернути" (mirror) свідомо НЕ додано** — осесиметричний прямокутник чи коло виглядає
  однаково до і після дзеркалення, кнопка була б пустушкою без жодного видимого ефекту.
- **Тінь і z свідомо відсутні** — це властивості спрайту-плейсменту (`tileId`, зображення),
  а колізія — це чиста форма без картинки, тіні й z-порядку їй концептуально не потрібні
  (сам користувач це підтвердив у проханні).
- Дії `del`/`cdup`/`clock`/`cunlock` — усі в `else`-гілці (`selected.type!=='placement'`)
  обробника `selPanel.addEventListener('click', ...)`, аналогічно за структурою до
  `lock`/`unlock`/`del` для плейсментів вище в тому ж файлі.

## Інструмент "Штамп" (`cloneMode==='stamp'`)

Реалізовано як ЧЕТВЕРТИЙ під-режим існуючого інструмента "Клон" (`line`/`fillrect`/
`filldiamond`/`stamp`), а не окрема кнопка в нижній панелі — нижня панель інструментів вже
щільна (7 кнопок), додавати восьму без переробки layout не варто. `modeBar` для `tool==='clone'`
вже мав патерн перемикання під-режимів кнопками — просто додано туди ще один пункт з
іконкою `🖨 Штамп` (нема окремого рядка перекладу `cloneStamp` в `translations` — іконка
підставляється напряму в JS, а не через `t()`, оскільки текст той самий у всіх мовах).

**Як зберігається штамп:** нова кнопка `🖨 Штамп` на панелі ГРУПОВОГО виділення
(`data-act="multi-savestamp"`, поруч з `multi-copy`/`multi-move`/`multi-del`). Математика
ідентична `multi-copy` (те саме обчислення `dx`/`dy` відносно центру bbox виділення), але
результат кладеться не в `clipboard`, а в окрему змінну `currentStamp = {items:[...]}` —
навмисно ОКРЕМА від `clipboard`, щоб збереження штампу не затирало те, що людина, можливо,
скопіювала через звичайний `Ctrl+C`/`dup`, і навпаки. Одразу після збереження — авто-перемикання
`tool='clone'; cloneMode='stamp';` (той самий патерн "одразу став зручний інструмент", що і
з тінню/копіюванням).

**Як штампується:** `tool==='clone' && cloneMode==='stamp'` вставлено в ДВА місця:
1. `pointerdown`: у гілці, де раніше `cloneMode!=='line'` автоматично означало
   "малювати прямокутник/ромб" (`mode='drawShape'`) — додано виняток `&& cloneMode!=='stamp'`,
   інакше stamp-тап хибно трактувався б як старт малювання фігури. Тепер для `stamp` (як і для
   `line`) виконання провалюється до `mode='tapPending'` — це проста точка дотику, без
   протягування прямокутника.
2. `pointerup` у блоці `mode==='tapPending' && !moved`: якщо `currentStamp` порожній —
   toast з підказкою зберегти штамп спочатку; інакше створює копію КОЖНОГО елемента
   `currentStamp.items` зі зсувом `dx`/`dy` відносно точки дотику (з урахуванням snap, якщо
   увімкнений), на активному шарі, з `newPlacementZ`... ні, з тим самим `z`, що був
   збережений в `it.z` (тобто оригінальні відносні z всередині групи зберігаються, а не
   перераховуються заново — так само, як при звичайному paste `multi`).

**Свідомо не зроблено:** неперервне "малювання" штампом під час перетягування (кожен новий
тап — один штамп, не brush-style кілька штампів по дорозі пальця). Якщо захочеться такої
поведінки — дивитись, як `mode==='drawShape'` реалізовано для `fillrect`/`filldiamond` і
переробити аналогічно, або просто примусово ставити штамп на кожному `pointermove`, поки
кнопка натиснута (з дедуплікацією за grid-коміркою, щоб не заспамити один нацл сотнями копій).

`currentStamp` НЕ зберігається в `serializeProject()`/`loadProjectData()` — сесійний стан,
як і `clipboard`, `selPanelHidden`, `selPanelCustomPos`.
