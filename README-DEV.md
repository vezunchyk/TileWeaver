# TileWeaver — довідка для розробки (для себе / для іншого ШІ)

Один файл `index.html` (~6000 рядків, HTML+CSS+JS, без збірки, без залежностей крім Google
Analytics тегу). Живе на https://tileweaver.online. Немає бекенду.

**Попередній README (`README-DEV-19-1-1.md`) застарів і описував ІНШИЙ робочий процес**
(файл називався `map-editor.html`, згадувались `help.html`, Playwright-тести, генерація
favicon/sitemap Python-скриптами, GitHub Pages деплой). Це може досі бути правдою для
екосистеми навколо проєкту (сам сайт, SEO, довідкова сторінка) — але **в цьому середовищі
я не маю доступу до тих файлів і не можу підтвердити їхній поточний стан.** Цей README
описує ТІЛЬКИ те, що реально є у файлі `index.html`, який мені дають на редагування.
Якщо користувач згадає `help.html`, favicon, sitemap — запитай, чи є в нього ці файли, не
припускай.

**Головне правило роботи над цим файлом:** перед правкою — `grep -n` за назвою функції чи
за унікальним рядком тексту (HTML) з коду нижче, щоб знайти ТОЧНЕ місце. Файл великий,
переписувати блоками "на пам'ять" — ризиковано (легко зламати дужки/кому в довгому
ланцюжку `+` для рядків HTML, як уже траплялось — див. "Часті практичні граблі" нижче).

Після КОЖНОЇ правки, без винятків:
1. `node --check` на витягнутий вміст найбільшого `<script>` блоку (```python
   re.findall(r'<script>(.*?)</script>', html, re.S)```, взяти `max(..., key=len)`) —
   ловить синтаксичні помилки.
2. Порівняти всі `id="..."` в HTML з усіма `getElementById('...')` в JS — ловить друковані
   помилки в іменах id (типовий наслідок копіювання блоків).
3. Порахувати `<div\b` vs `</div>` — ловить розбалансовані теги після ручних вставок/видалень
   шматків HTML (сталось двічі за час роботи над цим файлом через необережний `str_replace`).
4. Живого браузера/Playwright у цьому середовищі НЕМА (мережа для завантаження Chromium
   недоступна) — тестування суто статичне (пп 1-3). Реальну перевірку жестів/UI на
   пристрої робить сам користувач; явно про це казати, не видавати статичну перевірку за
   "протестовано".

## Модель даних (`project`)

```js
project = {
  id, name,
  gridType: 'iso' | 'isoAsym' | 'isoPixel' | 'top' | 'side',
  cellSize,
  tiles: {
    tileId: {
      name, img, dataURL, folderId,
      animFrames, animFrameMs,        // рівномірна анімація (смуга N однакових кадрів)
      frames: [{x,w,pivotX,pivotY}],  // АБО кадри РІЗНОЇ ширини (двері тощо) — взаємовиключно з animFrames по суті
      pivotX, pivotY,                 // 0..1, фракція від розміру ОДНОГО кадру/усього тайла
      anchor: 'bottom',               // легасі-поле старих тайлів без pivot-редактора
      edgeAnchorT,                    // 0..1, точка на периметрі клітинки (замінює старе gridAnchor)
      gridAnchor                      // легасі рядок ('top'|'right'|'bottom'|'left'), читається якщо edgeAnchorT нема
    }
  },
  placements: [
    { id, tileId, x, y,              // ЦІЛІ пікселі (px() round), принципово
      z,                              // АБСОЛЮТНЕ число, жодної формули з baseZ шару
      layerId, scaleX, scaleY, flipX, flipY, rotation, skewX,
      locked,                         // boolean — не рухається/не ресайзиться, підвищений допуск для розблокування
      group,                          // текст, напр. "house_03" — обʼєднує в будинок
      floor,                          // число, номер поверху (взаємовиключне з isRoof)
      isRoof                          // boolean, дах — не займає простір номерів поверхів
    }
  ],
  collisions: [
    { id, shape:'rect', x0,y0,x1,y1, type, locked, group, floor, fromFloor, toFloor } |
    { id, shape:'circle', x,y,r, type, locked, group, floor, fromFloor, toFloor }
  ],  // type: 'solid' (типово, поле може бути відсутнє) | 'trigger' | 'floorTransition'
  spawns: [ {id, x, y, spawnType, chance} ],  // spawnType — довільний текст, не enum
  layers: [ {id, name, visible, locked, baseZ} ],
  activeLayerId,
  autotileGroups: [
    { id, name, gridType:'iso',
      corners:{TL,TR,BR,BL}, // 4 РІЗНІ tileId матеріалів
      edges:{N,E,S,W} }      // крайові тайли між сусідніми кутами (N=TL↔TR, E=TR↔BR, S=BR↔BL, W=BL↔TL)
  ],
  tileFolders: [ {id, name} ]
}
```

**Ключове правило**: `p.z` (обʼєкта) і `layer.baseZ` — два НЕЗАЛЕЖНІ виміри. Не зливати
знову в одну формулу — це вже було й зламало сортування між шарами (див. історію нижче).

## Глибина малювання (`comparePlacements`) — чинна модель

```js
comparePlacements(a,b) = ((a.z||0)-(b.z||0)) || (a.y-b.y)
```

`p.z` — абсолютне число, `baseZ` шару в сортуванні НЕ бере участі взагалі.

- `layer.baseZ` — лише підказка, з якого числа почнуться НОВІ обʼєкти на цьому шарі:
  `newPlacementZ(layerId) = getLayer(layerId).baseZ + 1`. Однакове число для будь-якої
  кількості нових обʼєктів за одну операцію (заливка, розкид) — НЕ лічильник, що росте
  з кожним обʼєктом (це вже було причиною "космічних" z-чисел, виправлено).
- `LAYER_Z_STEP = 10`. Новий шар отримує `baseZ = nextLayerBaseZ()` = максимум `baseZ`
  серед ІСНУЮЧИХ ЗАРАЗ шарів `+10`, рахується щоразу наново, нічого не зберігається як
  персистентний лічильник (видалення шару не чіпає `baseZ` інших).
- Кнопка "Підняти"/"Опустити" шар впливає ТІЛЬКИ на те, з якого числа почнуться майбутні
  нові обʼєкти — вже розміщені не перемальовуються заднім числом.
- `merge()` (об'єднання видимих шарів) НЕ рахує жодної арифметики над `p.z` — тільки
  перепризначає `layerId`.
- **Жодного автоматичного масового переписування `z`/`baseZ` ніде** — свідома вимога:
  "не потрібно робити формули, які все ламають". Якщо в старих даних лишились "космічні"
  числа з дуже старих версій — це очікувано, виправляти вручну через кнопку "Порядок".
- Кнопки "▲"/"▼" в панелі дій (одиночний і груповий варіант) зсувають `z` на ±1; кнопка
  з числом (`layer`/`multi-zEdit`) відкриває `prompt()` з поточним значенням.

## Типи сітки (`project.gridType`) — три різні ізометричні математики, не плутати

Усі три ВІЗУАЛЬНО схожі (ромб 2:1), але мають різну внутрішню механіку — не переносити
код з однієї в іншу без розуміння різниці:

1. **`'iso'`** — чиста симетрична математика: `hw = cellSize/2, hh = cellSize/4`,
   `isoCell(c,r) = {x:(c-r)*hw, y:(c+r)*hh}`, `invIso` — обернена. Лінія сітки малюється
   растровим Bresenham-подібним штампом (`window.isoGridStamp`, побудований `fillRect`
   по клітинках) — НЕ векторним `ctx.stroke()`, бо canvas завжди згладжує похилі лінії
   (`imageSmoothingEnabled` не діє на лінії, тільки на картинки).
2. **`'isoAsym'`** — точна пікселна маска, зчитана з референсного зображення користувача
   (не математично симетрична — верх/право/низ/ліво НЕ дзеркальні одне одному, є реальний
   зсув на 1-2px через те, як растеризувалась стара текстура). Константи
   `ISO_ASYM_MASK_RUNS`, `ISO_ASYM_BASE=64`, окремі `isoAsymCell`/`invIsoAsym` (розміщення)
   і ОКРЕМІ `ISO_ASYM_TILE_COL/ROW` вектори для ЛІНІЇ СІТКИ (`invIsoAsymTile`) — вони не
   збігаються один з одним, бо крок реального растрового патерна відрізняється від
   геометричного кроку розміщення клітинок.
3. **`'isoPixel'`** ("Ізо (Unity)") — **розміщення (cellToWorld/worldToCell/
   diamondVertices) ІДЕНТИЧНЕ до `'iso'`** (перевірено вимірюванням: попри те, що
   растрова маска, яку намалював користувач для Unity, виглядала асиметрично, її
   справжні вершини математично збігаються зі стандартним симетричним 2:1 — асиметрія
   була візуальним артефактом непарної висоти зображення, не реальним зсувом). Єдина
   різниця — **окремий растровий штамп лінії сітки** (`ISO_PIXEL_MASK_RUNS`,
   `buildIsoPixelStamp`), знятий піксель-в-піксель з наданого зображення (включно з тим,
   що низ не сходиться в гостру точку — останній крок сходинки "з'їдає" сусідній тайл
   при стикуванні, так само як в оригіналі користувача). Якщо колись знадобиться ЩЕ один
   схожий "піксель-точний" тип сітки під інший референс — копіювати саме цей патерн
   (спільна математика розміщення + власний штамп), а не `isoAsym`.

Диспетчери `cellToWorld`/`worldToCell`/`diamondVertices`/`drawDiamondOrSquare` містять
`if(gridType==='iso' || gridType==='isoPixel') ...` — якщо додаєш ЩЕ один тип сітки з
такою ж математикою розміщення, шукай усі такі умови (`grep -n "gridType==='iso'"`) і
додавай туди ж, а НЕ дублюй логіку.

`'top'`/`'side'` — звичайна квадратна сітка, `cellToWorld` рахує ЦЕНТР клітинки (не
кут) для обох.

## Збереження: IndexedDB + localStorage (найважливіше для стабільності)

**Історія проблеми:** усе (включно з base64-картинками всіх текстур) спершу писалось у
`localStorage`, а в нього жорсткий ліміт ~5-10МБ на весь сайт. Кілька текстур середньої
якості — і ліміт вичерпано; при переповненні `setItem` кидає виняток і НЕ записує
НІЧОГО (не частково). Користувач бачив "малюю — тисну зберегти — а після перезавантаження
нічого нема" і хибний банер "сховище переповнене" навіть коли технічно мало б вистачати.

**Поточна архітектура:**
- **IndexedDB** (`IDB_NAME='tileweaver-db'`, `IDB_STORE='projects'`) — самі дані проєкту
  (усе, що повертає `serializeProject()`, включно з `dataURL` картинок). Ліміт — частка
  вільного місця на диску (типово сотні МБ+), а не фіксовані мегабайти.
- **`localStorage`** — лишився ТІЛЬКИ для легких речей: `IDX_KEY`
  (`zone-edit-projects-index`, список `{id,name,updatedAt}` БЕЗ картинок) і `ACTIVE_KEY`
  (`zone-edit-active-project`, просто id рядком). Ці ніколи не впруться в ліміт.
- **Міграція старих даних прозора**: `loadProjectDataById(id)` спершу питає IndexedDB;
  якщо там порожньо — читає СТАРИЙ localStorage-ключ (`projectKey(id) =
  'zone-edit-project-'+id`) і одразу (у фоні, не чекаючи) переносить знайдене в
  IndexedDB. Це означає: НЕ можна просто видалити стару `projectKey`-логіку "для
  чистоти" — вона досі потрібна як шлях міграції для користувачів зі старими даними.
- **Усі операції з IndexedDB асинхронні** (`idbGet`/`idbSet`/`idbDelete` повертають
  Promise). `flushSaveActiveProject()` через це теж асинхронна — має лічильник
  `saveSeqByProject` (пер-проєкт), щоб пізніший `.then()` не переписав ІНДЕКС
  застарілим знімком, якщо два flush пішли близько один за одним (сам порядок ЗАПИСУ
  даних у IndexedDB гарантований специфікацією за порядком СТВОРЕННЯ транзакцій, це
  захист лише для похідного кроку — оновлення `idx`/`ACTIVE_KEY` після запису).
- **Дебаунс** (`saveActiveProject()`, 400мс) для дрібних дій; `flushSaveActiveProject()`
  — примусовий негайний запис. **Кожне місце, де `project` підмінюється** (перемикання
  проєкту, імпорт, `createProject`) МУСИТЬ спершу викликати `flushSaveActiveProject()`
  для СТАРОГО стану — інакше останні 400мс змін губляться. Уже розставлено у
  `createProject()`, `openProjects()`, обробнику вибору проєкту зі списку, імпорті.
- **Синхронне збереження при закритті/згортанні вкладки НЕ гарантоване на 100%** —
  `beforeunload` майже не спрацьовує на мобільних при звичайному згортанні застосунку
  (ОС може заморозити/вбити вкладку без попередження JS). Тому є ТРИ хуки одразу:
  `beforeunload`, `visibilitychange` (`document.hidden`), `pagehide` — перші два
  покривають більшість мобільних сценаріїв, третій — запасний для окремих браузерів.
  Кнопка "💾 Зберегти" (`manualSaveBtn`) — ручний запобіжник поверх цього, не сам фікс.
- **Немає окремого `fileModal`** (старого дубльованого шляху експорту/імпорту) — був
  видалений, бо існував ПАРАЛЕЛЬНО з новим `projectsModal`-експортом, не чистив BOM
  при імпорті, і найімовірніше саме він показував хибне "файл пошкоджений". Один шлях:
  `projectsModal` → "⬇ Експорт у файл" / "⬆ Імпорт з файлу".
- **Експорт СТВОРЮЄ НОВИЙ ФАЙЛ щоразу** (не перезаписує той самий) — `File System
  Access API` (`showSaveFilePicker`, дозволив би перезапис) не підтримується на
  мобільних браузерах узагалі, тож був прибраний як марна складність. Це чесне
  обмеження браузера на телефоні, не забувати пояснювати користувачу, якщо спитає ще
  раз — не намагатись "полагодити" повторно без нового способу (десктопна
  File System Access API-гілка технічно можлива, якщо колись попросять саме для ПК).
- Імпорт: чистить BOM (`\uFEFF`) з початку файлу перед `JSON.parse` (типова причина
  хибного "файл пошкоджений" — деякі android-застосунки дописують BOM при збереженні/
  пересиланні файлу, сам JSON лишається валідним). При помилці парсингу показує РЕАЛЬНЕ
  повідомлення помилки (`err.message`), не просто "пошкоджений". Новий `id` генерується
  як `'proj_'+Date.now()+'_'+Math.random().toString(36).slice(2,7)` (не лише `Date.now()`
  — щоб не зіткнутися при двох операціях впритул).

## Панель дій виділеного обʼєкта (`#selPanel`) — сітка іконок 3×5 з налаштуванням порядку

**Кардинальна переробка** за проханням користувача (було: рядки кнопок з текстом,
різна ширина панелі, забагато порожнього місця, легко випадково влучити в сусідню
кнопку). Тепер:

- Фіксована сітка **3 стовпці × 5 рядів = 15 видимих значків**, розмір панелі завжди
  однаковий незалежно від того, скільки дій зараз доступно. Якщо дій більше 15 —
  внутрішній скрол (`.sel-grid{ overflow-y:auto; max-height:calc(5*42px+4*2px); }`).
- **Жодних текстових підписів на кнопках** (тільки іконка + `title`-тултип), КРІМ
  кнопки "Порядок" (`layer`/`multi-zEdit`) — там саме число і Є корисною інформацією,
  тому воно показується напряму (обрізається до 4 символів + "…", якщо задовге —
  `fmtZForBtn()`).
- **Один спільний реєстр** усіх можливих дій УСІХ типів виділення разом
  (`PANEL_ACTION_NAMES`/`PANEL_ACTION_ICONS`, ~24 ключі: `eye, copy, move, layer, zUp,
  zDown, group, floor, roof, houseMode, selectHouse, mirror, mirrorY, rotate, precision,
  shadow, shadowOval, stamp, autotile, lock, unlockGroup, dup, spawnEdit, ctype, del`)
  і **ОДИН налаштовуваний порядок** (`localStorage['zone-edit-panel-order']`, JSON-масив
  ключів). Кожен виклик `updateSelPanel()` для кожного типу виділення (одиночний тайл,
  заблокований тайл, група/multi, спавн, колізія) будує масив `items` лише з тих
  ключів, що СТОСУЮТЬСЯ поточного стану (наприклад `floor`/`roof` тільки якщо
  `p.group` заданий), і передає в `renderIconGrid(items)` — та сама функція
  впорядковує їх за збереженим порядком і рендерить `<div class="sel-grid">`. Ключі,
  яких нема серед `items` для поточного контексту, просто пропускаються — тому
  налаштовувати треба ОДИН РАЗ, а не окремо для кожного типу виділення.
- **Меню → 🎛 Налаштування панелі дій** (`panelSettingsModal`) — два списки: "У панелі"
  (з ↑/↓/✕) і "Доступні" (з "+"). `PANEL_DEFAULT_ORDER` — початковий порядок, кнопка
  "Скинути" повертає до нього.
- **`touch-action` на кнопках сітки — окрема пастка**, вже наступали: `touch-action` НЕ
  успадковується від контейнера до дітей автоматично (на відміну від майже всіх інших
  CSS-властивостей). `.sel-grid{touch-action:pan-y}` саме по собі НЕ гарантує, що дотик,
  який почався на КНОПЦІ всередині, теж вважатиметься `pan-y` — довелось прописати
  `pan-y` явно на самих кнопках (`#selPanel .sel-grid button{touch-action:pan-y}`), і
  окремо `touch-action:none` саме на кнопці "око" (`panelEye`) — вона не скролить, а
  перетягує всю панель (утримання), і якби успадкувала `pan-y`, нативний скрол бився б
  з ручним JS-драгом (панель "смикалась"). Якщо коли-небудь додаси ще одну кнопку з
  особливою поведінкою жесту всередині сітки — памʼятай про це явно, не покладайся на
  успадкування.
- Клік по кнопках у панелі — ОДИН делегований `selPanel.addEventListener('click', ...)`
  зчитує `e.target.closest('button').dataset.act` — тому сам рендер (`renderIconGrid`)
  можна міняти вільно (порядок/іконки/розкладку), не чіпаючи величезний
  `if/else if` ланцюжок обробки дій нижче в тому ж файлі.
- **Кнопка "око" (`panelEye`)**: короткий тап ховає/показує панель
  (`selPanelHidden`), утримання (400мс без руху >8px) — перетягує панель в довільне
  місце екрана, позиція запам'ятовується (`selPanelCustomPos`, сесійна змінна, НЕ
  зберігається в проєкті).

## Блокування (`p.locked` / `s.locked`) і групи/будинки

- **Кнопка блокування не потребує підтвердження, розблокування — потребує** (пряма
  вимога користувача, `confirm()` тільки на unlock).
- **Розблокування ЦІЛОЇ групи одним тапом**: панель заблокованого тайла (якщо
  `p.group` заданий) показує окрему кнопку `unlock-group` — знаходить УСІ плейсменти з
  тим самим `group` і знімає `locked` з усіх одразу. Раніше цього не було, і
  користувач, розблокувавши один тайл будинку, продовжував натикатись на "заблоковано"
  на кожному наступному тайлі того самого будинку — треба було або клікати
  тайл-за-тайлом, або спершу "обрати всю групу" (окрема кнопка) і ЛИШЕ ПОТІМ
  розблокувати в іншій, груповій панелі (два кроки, які легко пропустити).
- **`selected.houseGroup`** — поле на обʼєкті мультивиділення (`selected.type==='multi'`),
  каже, чи вся ця група вже належить ОДНОМУ спільному будинку (тоді показуються
  Поверх/Дах/Режим будинку). Рахується (а) при виділенні рамкою — перевіряє, чи всі
  виділені тайли мають ОДНАКОВИЙ `group`; (б) при вставці (paste) — якщо всі вставлені
  тайли походять з ОДНІЄЇ групи оригіналу; (в) явно виставляється після кнопки "Група"
  для мультивиділення. Якщо додаси ще один спосіб створити `selected={type:'multi',...}`
  — не забудь порахувати `houseGroup` так само, інакше Поверх/Дах не з'являться, доки
  користувач не натисне "Група" вручну ще раз (саме цей баг уже був і виправлений).
- **Копіювання/Штамп будинку — ОБОВ'ЯЗКОВО генерує НОВУ назву групи**, не переносить
  стару як є. Причина: старий код робив `np.group = it.group` напряму — при
  копіюванні/паст цілого будинку копія й оригінал ставали ОДНІЄЮ групою (lock/unlock,
  house mode, вибір "усього будинку" зачіпали б обидва одночасно), а для **Штампа** це
  було ще гірше — кожна ОКРЕМА постановка штампа (кожен тап) теж брала `it.group`
  напряму, тобто 5 проштампованих копій + оригінал = одна спільна група. Фікс: у ОБОХ
  місцях (`doPaste()` для `clipboard.type==='multi'`, і stamp-постановка) є локальна
  мапа `groupRemap = {}` — для кожної ЗУСТРІНУТОЇ старої назви групи генерується ОДНА
  нова (`'house_'+Date.now()+'_'+Math.random().toString(36).slice(2,7)`), однакова для
  всіх елементів ЦІЄЇ конкретної вставки/постановки, але РІЗНА між різними вставками.
  Якщо додаси ще один шлях масового копіювання плейсментів з `group` — повтори цей
  патерн, а не `np.group = it.group`.
- **`selectHouse`** (🔎, іконка навмисно НЕ 👁 — той символ уже зайнятий кнопкою
  видимості шару, було плутано) — шукає всі плейсменти з тим самим `group`, з УСІХ
  шарів, і формує з них `selected.type==='multi'`.

## Анімовані тайли — два РІЗНІ механізми, не плутати

1. **Рівномірна анімація** (`tile.animFrames`, `tile.animFrameMs`) — горизонтальна
   смуга N ОДНАКОВИХ за шириною кадрів в одному PNG. `img.naturalWidth` — ширина ВСІЄЇ
   смуги; `placementBBox()` ділить на `animFrames` централізовано (використовується
   всюди: хіт-тест, ручки, мінімапа, тінь). Малювання поточного кадру — 9-аргументний
   `drawImage(img, sx, sy, sw, sh, dx, dy, dw, dh)`, `sx = getAnimFrameIndex(tile) *
   frameW`. `getAnimFrameIndex` рахує кадр як функцію часу від спільної точки відліку
   `animStartTime` — не окремий лічильник на тайл. Фоновий `setInterval` (60мс,
   `registerAnimatedTile`) сам себе зупиняє, якщо `hasAnyAnimatedTile()` поверне false.
2. **Кадри РІЗНОЇ ширини** (`tile.frames: [{x,w,pivotX,pivotY}]`, напр. двері: зачинені
   вужчі за відчинені) — `hasVariableFrames(tile)`. Редагується через ОКРЕМИЙ
   повноекранний редактор (`openFrameMark`, межі кадрів тягнеться пальцем, а не
   вводиться числом; pinch-zoom; кожен кадр має власний `pivotX/pivotY` фракцією від
   СВОГО `w`, не від ширини всієї смуги). Ці два поля (`animFrames` і `frames`) по суті
   взаємовиключні в тому, як художник готує тайл, але код це явно не забороняє —
   перевіряй `hasVariableFrames` ПЕРШИМ там, де логіка для двох механізмів розходиться
   (напр. розрахунок ширини для тіні: `hasVariableFrames(tile) ? tile.frames[0].w :
   img.naturalWidth/tile.animFrames`).

GIF **свідомо не підтримується** (canvas 2D не програє GIF-анімацію сам; підключення
сторонньої бібліотеки розпаковки означало б першу зовнішню залежність у самодостатньому
файлі) — якщо попросять "а зробіть GIF", нагадати про це рішення, не переписувати мовчки.

## Панель точного розміщення (🎯) і pivot-стрілочки — інверсія напрямку

Обидві речі рухають ОБ'ЄКТ на екрані, а не сирі внутрішні координати напряму — і це
принципово, бо pivot і видиме положення текстури повʼязані ОБЕРНЕНО:
`x0 = ax - iw*pivotX` (те саме по Y). Якщо кнопка "→" мала б штовхати текстуру вправо
на екрані — вона повинна ЗМЕНШУВАТИ `pivotX`, не збільшувати. Уже була помилка, коли
знаки не інвертували — усі чотири напрямки (стрілочки корекції pivot біля живого
прев'ю, `pivotNudgeStep`) виявились дзеркально переплутані. Якщо додаси ще один
UI-елемент, що рухає обʼєкт через зміну pivot (а не через `p.x/p.y` напряму) —
перевір знак на реальному прикладі, не покладайся на "очевидну" відповідність.

- **🧲 Клітинка / 🎯 Піксель** — два режими кроку в панелі точного розміщення:
  клітинка рухає на РІВНО один крок сітки (`cellToWorld(1,0)` мінус `cellToWorld(0,0)`
  і так по осях), піксель — на 1/2/4/8 світових пікселів напряму. Довге утримання
  стрілочки (350мс затримка, потім кожні 90мс) повторює крок.
- Прев'ю (і живе прев'ю pivot, і міні-прев'ю в редакторі кадрів) **раніше "тремтіло"**:
  рамка авто-масштабування (fit) рахувалась від ФАКТИЧНОЇ позиції текстури (`x0/y0`),
  тому кожен зсув pivot на 1px трохи зсував і саму "камеру" прев'ю слідом за текстурою
  — сітка виглядала так, ніби сама рухається. Фікс: рамка тепер рахується від
  НАЙГІРШОГО можливого розміщення (`ax±iw`, `ay±ih` — pivot завжди 0..1, тому діапазон
  відомий заздалегідь), а не від поточного `x0/y0`. Якщо додаси ще одне прев'ю з
  auto-fit — рахуй межі так само, не від живих координат об'єкта.

## Прив'язка/snap (`snapPoint`) і `touch-action` в цілому

`snapPoint` — диспетчер, що йде через ті самі `worldToCell`/`cellToWorld`, що й
розміщення; окремої логіки на сітку нема (якщо прив'язка "не працює" на конкретному
типі сітки — спершу перевір, чи цей `gridType` доданий у ВСІ диспетчери, а не сам
`snapPoint`, і чи не CSS/`touch-action`-конфлікт заважає жесту дійти до канваси
взагалі — обидва випадки вже траплялись і виглядали як "не працює прив'язка",
хоча причина була не в математиці).

`#canvasWrap` має `touch-action:none` (щоб не заважати панорамуванню карти пальцем) —
це значення потрібно ЯВНО переоголошувати (`pan-y`/`auto`/`none` за потребою) на КОЖНОМУ
елементі всередині, який має власну прокрутку чи жест, не покладаючись на те, що
"воно якось саме розбереться" — не покладається, `touch-action` не успадковується.

## Часті практичні граблі (з історії правок цього файлу)

1. **`str_replace`/ручна вставка HTML-блоку може випадково "з'їсти" сусідній тег**, якщо
   старий і новий рядок не збігаються рівно по краю (типово — забути перенести
   `<div class="modal-bg" id="...">`, що стояв одразу після місця вставки). Завжди
   рахувати баланс `<div>`/`</div>` після ручних вставок модалок.
2. **CSS-специфічність при перевикористанні класів для стилю кнопок**: якщо є і
   `#selPanel button{...}` (загальне), і `.sel-grid button{...}` (спеціальне для
   сітки) — ID-селектор переможе клас НЕЗАЛЕЖНО від порядку в файлі. Потрібно
   `#selPanel .sel-grid button{...}`, щоб спеціальні стилі реально застосувались.
3. **`touch-action` — не успадковується.** Див. два окремі розділи вище (панель дій,
   snap) — та сама помилка трапилась двічі поспіль, поки не запам'ятав.
4. **Один розповсюджений CSS-клас для НЕспоріднених елементів** (`.grid-type-row`
   колись висів і на реальному перемикачі сітки, і на кнопках зовсім інших модалок) —
   спільний клас, на якому висить JS-обробник з побічним ефектом (зняти `active` з
   УСІХ елементів цього класу на сторінці), небезпечний, якщо клас використовується
   ще й просто "заради стилю" деінде. Для суто візуального повторного використання
   стилю без спільної JS-поведінки — заводити окремий клас (`.btn-row`), не ділити з
   функціональним.
5. **`document.querySelector('...active')` повертає ПЕРШИЙ збіг у порядку DOM**, не
   обов'язково той, що в потрібній модалці — якщо десь є елемент з тим самим класом
   і атрибутом `class="active"` ЗАДАНИМ ПРЯМО В HTML за замовчуванням (а не через JS),
   і він стоїть РАНІШЕ в розмітці — саме він "виграє" запит, а не очікуваний.
6. **Перевіряти ВСІ місця з однаковою умовою** (`grep -n "gridType==='iso'"`), коли
   додаєш новий варіант — легко забути один з 5-10 розкиданих по файлу диспетчерів
   (`cellToWorld`, `worldToCell`, `diamondVertices`, `drawDiamondOrSquare`, рендер
   лінії сітки в `render()`, той самий рендер у живому прев'ю `lpDrawGridStamp`,
   підсвітка вибраної клітинки, `cellFitScale`-подібні розрахунки висоти).

## Свідомі спрощення (не баги, не чіпати без нового прохання)

- Маркери виділення/хіт-тест не обертаються разом з обʼєктом (axis-aligned bbox завжди).
- Тінь (`shadow`/`shadowOval`) — фіксований відсотковий офсет, не піксель-точна
  детекція контакту з землею.
- Автотайлінг: без обертання/дзеркалення країв, без окремих тайлів для потрійних кутів
  (де сходяться 3+ матеріали) — "варіант А", узгоджено з користувачем.
- Колізіям немає тіні/z/дзеркалення (осесиметрична форма виглядає однаково до/після) —
  концептуально не потрібні для чистої форми без картинки.
- Точки спавну не мають хендлів масштабу/повороту (не мають розміру).
- Розкидання (`scatter`): "частота" — не точна кількість, а відсоток від теоретичного
  ліміту пакування кіл заданого радіуса в площі — прямо за проханням користувача.
- Undo (`pushUndo`) охоплює `placements/collisions/spawns/layers/activeLayerId` — НЕ
  налаштування конкретного тайла (анімація/pivot/edge-anchor/автотайл-групи/назва
  проєкту/тип сітки). Це свідомий компроміс (інакше кожен снепшот тягнув би за собою
  словник тайлів з картинками), але поведінково це НЕ "звичайний Ctrl+Z усього" — якщо
  користувач поскаржиться, що Undo не повернув зміну pivot/анімації, це очікувано,
  а не баг.

## Якщо щось "не працює на новому типі сітки/новій фічі" — порядок діагностики

1. Спершу перевір координатну математику ізольовано (написати маленький тест round-trip
   `cellToWorld → worldToCell` для кількох точок) — перш ніж підозрювати щось складніше.
2. Якщо математика правильна, а "на екрані не працює" — підозрюй `touch-action` і
   CSS-специфічність РАНІШЕ, ніж JS-логіку. Обидва вже були реальною причиною двічі.
3. Перевір, чи новий `gridType`/ключ дії доданий у ВСІ диспетчери (`grep`), а не лише
   в очевидне перше місце, де ти його додав.
4. Тільки після цього — заглиблюйся в конкретну функцію жесту/дії.
